# Admitting a grader result

An interpreter name, container digest and successful process exit leave several
measurement questions open. Check the resolved interpreter, framework version
and module location, project revision and imported project bytes. A search path
can select a project helper as the test runner or use an installed package
instead of the source being evaluated.

For Python, the working directory and `PYTHONPATH` affect module discovery.
Isolated mode also ignores project paths supplied through the environment.
Inspect the actual child process and qualify import settings against the task.
Freeze any runtime changes across comparison conditions.
[Python command-line reference](https://docs.python.org/3.12/using/cmdline.html)

Use an unchanged input to establish the starting score. A grader that already
awards the maximum leaves no improvement headroom on that task. Keep the task
selection fixed for confirmatory analysis. Use exposed examples for development
and report the coverage and limitations of the frozen evaluation frame.

Separate three forms of missing output.

- A complete capture with no changes is a submitted candidate. Run the grader
  on that state and preserve its measured outcome.
- An incomplete capture leaves the submission unknown. Retain the attempt,
  diagnose the collection failure and withhold a score.
- A skipped check needs its declared cause. Missing candidate work can justify
  a task outcome when complete source evidence proves that cause. Unavailable
  infrastructure needs repair or adjudication. Keep the native denominator
  and every attempt in the accounting.

Require the expected testcase identities, terminal completion, native report,
exit status and score to agree. Keep auxiliary metrics in their actual units.
Publisher result tables, oracle controls and synthetic transport tests each
support their recorded scope. A claim that a skill improves an agent requires
independent task outcomes under the declared intervention.
